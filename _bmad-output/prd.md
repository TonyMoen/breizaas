# Product Requirements Document - Breizaas

**Author:** Tony-
**Date:** 2025-12-21

## Executive Summary

**Breizaas** is a professional artist website for an AI-generated Norwegian rural party music artist (bygdemusikk/festmusikk) who has achieved significant success with 125,000 monthly listeners on Spotify. This website serves as the artist's official digital presence, providing fans with a centralized hub for music discovery, tour information, merchandise, and booking inquiries.

The project addresses the need for a professional web platform that matches the artist's proven market success. With a substantial and growing fanbase, the artist requires a credible online presence where fans can engage with content, event organizers can explore booking opportunities, and new audiences can discover the unique intersection of AI technology and traditional Norwegian music.

The website will serve multiple user segments:

- **Existing fans** (125k monthly listeners) seeking tour dates, new releases, and merchandise
- **Event organizers** evaluating the artist for bookings and needing professional contact channels
- **New audiences** discovering the artist through search and social media
- **Media and press** requiring professional artist information and assets

All public-facing content will be presented in Norwegian to authentically serve the Norwegian music community, while the codebase will be maintained in English for technical clarity.

### What Makes This Special

This is not an experimental concept - it's a **proven success story**. An AI artist has already achieved legitimacy and substantial reach in the traditional Norwegian bygdemusikk genre. The website's role is to professionalize this success by providing:

- **Credibility**: A professional online presence that reflects the artist's 125k listener achievement
- **Fan engagement**: A centralized platform for an established fanbase to stay connected
- **Business infrastructure**: Professional booking and merchandise capabilities for a commercially viable artist
- **Cultural positioning**: Presenting AI-generated music within the authentic context of Norwegian rural music tradition

The site bridges innovation and tradition - modern technology (AI music, Next.js, API integrations) serving a traditional music genre, all while maintaining the professional standards expected of established Norwegian artists.

## Web Application Specific Requirements

### Project-Type Overview

Breizaas is a **server-side generated (SSG) web application** built with Next.js, leveraging traditional file-based routing for optimal SEO performance and user experience. The architecture prioritizes fast initial page loads, excellent search engine visibility for Norwegian market, and seamless integration with third-party services (Spotify, Bandsintown, Shopify, YouTube) while maintaining content flexibility through Sanity CMS.

### Technical Architecture Considerations

**Routing Architecture:**

- **Next.js File-Based Routing:** Traditional multi-page structure using Next.js App Router or Pages Router
- **Routes:**
  - `/` - Home page (hero section, featured content, stats)
  - `/music` or `/discography` - Music/discography overview
  - `/tour` - Tour dates (Bandsintown integration)
  - `/merch` - Merchandise store (Shopify integration)
  - `/about` - Artist bio and background
  - `/contact` or `/booking` - Contact/booking form
  - `/arrangor` - Hidden press kit page for event organizers
- **Static Site Generation (SSG):** All pages pre-rendered at build time for optimal performance
- **Incremental Static Regeneration (ISR):** Enable on-demand or time-based revalidation when Sanity CMS content updates
- **Client-Side Navigation:** Smooth transitions between pages using Next.js Link component

**Browser Compatibility:**

- **Target Browsers:** Modern browsers - latest versions of:
  - Chrome (desktop & mobile)
  - Firefox (desktop & mobile)
  - Safari (desktop & iOS)
  - Edge (desktop)
- **Mobile Browsers:** iOS Safari and Chrome on Android
- **No Legacy Support:** No IE11 or older browser support required
- **Progressive Enhancement:** Core functionality works without JavaScript, enhanced with JS where available

### Responsive Design Requirements

**Breakpoint Strategy:**

- **Mobile:** 320px - 767px (primary focus for on-the-go fans)
- **Tablet:** 768px - 1023px (browsing experience)
- **Desktop:** 1024px+ (event organizer evaluation, detailed browsing)
- **Large Desktop:** 1440px+ (optional optimization)

**Design Principles:**

- Mobile-first approach
- Touch-friendly interactive elements (minimum 44x44px tap targets)
- Responsive images with Next.js Image component (automatic optimization)
- Fluid typography and spacing
- Professional but clean layout matching established Norwegian artists

### Performance Targets

**Core Web Vitals (Target Scores):**

- **LCP (Largest Contentful Paint):** < 2.5 seconds
- **FID (First Input Delay):** < 100 milliseconds
- **CLS (Cumulative Layout Shift):** < 0.1
- **Overall PageSpeed Score:** 90+ on mobile and desktop

**Load Time Targets:**

- **Initial Page Load:** < 2 seconds on 3G connection
- **Time to Interactive (TTI):** < 3 seconds
- **Page Transitions:** < 500ms (client-side navigation)

**Optimization Strategies:**

- Next.js automatic code splitting
- Image optimization using Next.js Image component
- Lazy loading for below-the-fold content
- Font optimization (system fonts or optimized web fonts)
- Minimize third-party script impact (async/defer loading)
- CDN delivery for static assets

### Risk Mitigation Strategy

**Technical Risks:**

**Risk:** API integration complexity or rate limiting issues

- **Mitigation:** Use well-documented APIs (Spotify, Bandsintown, Shopify all have robust documentation), implement caching strategies to minimize API calls, use ISR to reduce build-time API dependencies
- **Contingency:** Start with iframe/widget embeds for faster MVP, migrate to full API integration post-launch if needed

**Risk:** Next.js migration from Vite introduces unforeseen technical challenges

- **Mitigation:** Leverage existing Vite site as complete reference, port components incrementally, Next.js has extensive migration documentation
- **Contingency:** Most React components port directly; routing is the primary change (file-based vs react-router)

**Risk:** Sanity CMS webhook/ISR integration complexity

- **Mitigation:** Sanity has excellent Next.js integration documentation and official plugins
- **Contingency:** Manual rebuild triggers as fallback until webhooks fully configured

**Risk:** Norwegian URL routing implementation

- **Mitigation:** Next.js supports custom routing easily through file naming or rewrites configuration
- **Contingency:** Standard English routes as fallback, though Norwegian URLs strongly preferred for authenticity

**Market Risks:**

**Risk:** Website doesn't convert Spotify listeners to engaged fans

- **Validation:** Prominent tour date display and easy merch access based on existing fan behavior patterns

## Non-Functional Requirements

### Performance

**NFR-P1: Page Load Performance**

- Initial page load must complete in < 2 seconds on 3G mobile connection
- Time to Interactive (TTI) must be < 3 seconds
- Client-side page transitions must complete in < 500ms

**NFR-P2: Core Web Vitals Compliance**

- Largest Contentful Paint (LCP) < 2.5 seconds
- First Input Delay (FID) < 100 milliseconds
- Cumulative Layout Shift (CLS) < 0.1
- Overall PageSpeed score ≥ 90 on both mobile and desktop

**NFR-P3: API Response Handling**

- Spotify API responses cached for minimum 1 hour to minimize API calls
- Bandsintown API responses cached appropriately for tour date freshness
- API failures must degrade gracefully with fallback content or error messages
- Maximum API response wait time of 5 seconds before timeout

**NFR-P4: Build Performance**

- Static site generation build time < 5 minutes for full site rebuild
- Incremental Static Regeneration (ISR) updates complete within 30 seconds of Sanity CMS content publish

### Security

**NFR-S1: Data Transmission**

- All pages must be served over HTTPS/TLS with valid SSL certificate
- All form submissions (contact, booking) must be transmitted securely over HTTPS

**NFR-S2: API Key Protection**

- All API keys (Spotify, Bandsintown, Shopify, Sanity, YouTube) must be stored as environment variables
- No API keys, secrets, or credentials exposed in client-side code or browser
- Content Security Policy (CSP) headers implemented to restrict script sources

**NFR-S3: Form Security**

- Contact and booking forms must include CSRF protection
- Form inputs must be validated and sanitized server-side
- Rate limiting on form submissions to prevent abuse (max 5 submissions per IP per hour)

**NFR-S4: Third-Party Integration Security**

- Shopify checkout handles all payment processing (PCI DSS compliance delegated to Shopify)
- No sensitive payment or user data stored on Breizaas infrastructure
- Sanity CMS access restricted to authorized artist admin only

### Accessibility

**NFR-A1: WCAG 2.1 AA Compliance**

- All pages must meet WCAG 2.1 Level AA standards
- Automated accessibility testing (axe, Lighthouse) must pass with zero critical violations

**NFR-A2: Perceivable Content**

- All images must have descriptive alt text
- Color contrast must meet minimum 4.5:1 ratio for normal text and 3:1 for large text
- Text alternatives provided for all non-text content

**NFR-A3: Operable Interface**

- All interactive elements must be keyboard accessible
- Focus indicators visible on all focusable elements
- No keyboard traps - users can navigate in and out of all interactive components
- Skip to main content link available on all pages

**NFR-A4: Understandable Content**

- Norwegian language specified in HTML lang attribute (nb-NO)
- Clear, consistent navigation across all pages
- Form validation errors displayed with clear, actionable error messages
- Consistent use of navigation patterns and interaction behaviors

**NFR-A5: Screen Reader Compatibility**

- Site must be fully navigable using screen readers (VoiceOver, NVDA, JAWS)
- Semantic HTML5 elements used throughout
- ARIA labels applied where needed for dynamic content
- Logical heading hierarchy (H1 → H2 → H3) maintained

### Integration Reliability

**NFR-I1: Spotify Integration**

- Spotify API integration must display artist profile, discography, and listener stats
- Graceful degradation if Spotify API unavailable (show cached data or fallback message)
- API rate limits respected to prevent service interruption
- Error states handled with user-friendly messaging

**NFR-I2: Bandsintown Integration**

- Tour dates must update within 1 hour of changes made in Bandsintown
- Integration must handle zero upcoming shows gracefully ("No upcoming tour dates")
- Past tour history accessible even if Bandsintown service temporarily unavailable (cached)

**NFR-I3: Shopify Headless Integration**

- Product catalog must sync with Shopify inventory in real-time or near-real-time
- Out-of-stock items clearly indicated
- Checkout process redirects to Shopify hosted checkout seamlessly
- Shopping cart state maintained during session

**NFR-I4: YouTube Integration**

- Video embeds must lazy load to prevent initial page weight impact
- Failed video loads handled gracefully without breaking page layout
- Video player responsive across all device sizes

**NFR-I5: Sanity CMS Integration**

- Content updates published in Sanity must trigger site rebuild within 30 seconds
- CMS webhook integration must be resilient to temporary network failures (retry mechanism)
- Preview mode available for content editors to review changes before publishing

**NFR-R1: Uptime**

- Website must maintain 99.9% uptime (< 8.76 hours downtime per year)
- Planned maintenance windows communicated in advance and scheduled during low-traffic periods

**NFR-R2: Error Handling**
